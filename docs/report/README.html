1. Legacy System Analysis

SVFRMS simulates one day of an indoor vertical farm. Four chamber threads (CH1 Tomato, CH2 Strawberry, CH3 Lettuce, CH4 Chili) each run 20 cycles. Each cycle reads five sensors (temperature, humidity, soil moisture, light, nutrient), checks every reading against hard-coded crop thresholds, raises alerts, charges water and energy, and puts device requests (for example "CH1|Cooling Fan") on a bounded queue of 5. A control thread takes requests off the queue and runs the device, which changes the chamber's state. At the end, two racing threads archive the alerts and print the daily report, and archive/daily_report.txt is written.

Everything is in one 393-line class, SVFRMS.java. Its main components are global public static state (lines 7–31), the ChamberState/ChamberSummary model (33–46), a string-switched event hub handleEvent (62–88), the rule engine processSensor (141–205), device control activateControl (90–129), a hand-written queue and ControlThread (131–139, 251–273), ChamberThread (275–295), reporting (207–241, 309–347), dead code (243–249, 297–307), and main (349–392).

2.2 Concurrency problems (spec 4.4)

Deadlock assessment. The only nested locking is alertLock → reportLock, taken in the same order in generateDailyReport and archiveAlerts, so no cycle can form and no deadlock is reachable as written. It is one edit away from the classic deadlock: if either method took reportLock first, each report thread could hold one lock and wait for the other. The real liveness risk is C10. Our design removes lock nesting entirely (section 5).

Spec gaps. The code has no severity levels and no sensor-failure alert (spec 3.4); we add both as an extension that leaves the legacy output untouched (section 6). Other gaps are documented, not changed, because spec 4 requires preserved behaviour: Heating Unit, Ventilation and Shade Controller do not exist (Humidifier and Dehumidifier do; we add a Heating Unit for the new crops only, section 6), only Tomato has every rule, and there is one combined report.

3. Proposed Design

Design rule: preserve behaviour exactly, and fix every smell and concurrency defect above. Every class exists to remove a specific problem. We captured the legacy output with a fixed seed and serial schedule, and our refactored output is byte-identical after normalization (timestamps and control-thread timing removed).

  • Crop rules as data. All 19 copied alert blocks became rows in crops.csv: crop, sensor, HIGH|LOW, limit, device, water, energy, message. * rows apply to every crop (the legacy global light and nutrient limits). SensorProcessor loops over whatever rules the registry holds and never names a crop. We chose a CSV over a Java catalogue class because adding a crop to a class is still "modifying existing code" (spec 4.2 ii).
  • One class per device behind a two-method Device interface. ControlService prints and records every activation in one place.
  • Observer for alerts. The rule engine publishes one Alert; the summary tracker, the alert store and the console printer each do one job.
  • Objects, not strings, on the queue. A ControlRequest holds the chamber, its state and the device.
  • Composition root. Only SVFRMS.createSimulation creates and connects objects; everything else gets its dependencies through its constructor, so the tests and the baseline harness can inject a seeded or fixed sensor source.
  • Fail fast on bad configuration. Every CSV error (unknown device or sensor, wrong column count, empty column, non-finite limit, negative cost, duplicate rule or chamber) stops the program before any thread starts, naming the file and line; a chamber whose crop has no rows gets a warning.

4. Final Architecture

End of the run (FarmSimulation.run): start the control consumer; submit one ChamberMonitor per row of chambers.csv and wait on each Future; call control.stop(), which queues a stop marker behind all pending requests so the queue drains first (giving up after 30 s if a device hangs), and check the control thread's own Future; then, on the main thread and in this fixed order, archive the alerts, print the report and save the file, plus alerts_by_severity.txt. If any chamber or the control thread failed, the error is printed and the program exits with status 1.

Deadlock freedom by construction. No method holds two locks at once. Each lock (ChamberState, ChamberSummary, AlertStore, the sensor log) is held only for a few field updates and never while calling another object; SensorProcessor holds no lock while it publishes an alert or waits to queue a request. With at most one lock held at a time, the lock-wait graph cannot contain a cycle.

Evidence. Legacy: 92/300 concurrent runs correct. Refactored run.jar: 300/300 correct with the 4 legacy chambers and 300/300 with the 7 demo chambers, with the same invariant checker. Seeded serial run on the 4 legacy chambers: normalized output identical to the legacy baseline. 48 JUnit test methods (60 runs, as the stress tests repeat 3 times), including stress tests that hammer every shared object from 8 threads × 5,000 operations, a producer-consumer test with a queue of 1, a failing-device test and a crashed-consumer test (C10), an interrupted-producer test (C9), a failing-chamber test (C11) and an interrupted-run test.

Crop extension (spec 4.5). Kale, Bok Choy, Bell Pepper and Eggplant were added as rows in crops.csv, with no Java changes; each automatically gets the shared light and nutrient rules. The default chambers.csv keeps the 4 legacy chambers, so a plain run behaves exactly as before. java -jar run.jar demo reads demo/chambers.csv, which adds CH5, Kale, CH6, Bok Choy and CH7, Bell Pepper without a rebuild (a notice names the override file); this 7-chamber layout also passes 300/300 concurrent runs. Only an explicitly named folder is read, so a stray CSV can never change a normal run. A chamber whose crop has no rows (a removed crop or a typo) keeps only the shared rules, as in the legacy code, and a start-up warning names the line.

Kale, SOIL, LOW, 40, Water Pump, 30, 0, WARNING, {crop} Low Soil Moisture  →  [CH5][Kale][ALERT] CH5 Kale Low Soil Moisture

Alerting extension (spec 3.4). Each rule now carries a severity column (temperature CRITICAL, humidity, soil and nutrient WARNING, light INFO). A new SeverityLog listener writes every alert with its level and a count per level to archive/alerts_by_severity.txt. A sensor that does not respond, or reports a reading outside its valid range in sensors.csv (NaN, humidity outside 0–100 %), raises a CRITICAL Sensor Failure alert; nothing is stored, no device runs and the chamber carries on. One extra console line ends the run, e.g. Alerts by severity: INFO=21, WARNING=64, CRITICAL=93; every legacy console line and the daily report are still identical to the legacy baseline.

7. Design Patterns

PatternWhereProblem it solves and why we chose it
StrategyDevice + 6 classesThe activateControl chain. Each device is a different algorithm behind one interface, so a new device never touches ControlService.
ObserverAlertPublisher → AlertListenershandleEvent did four jobs behind a string switch. The rule engine now raises one alert, and each listener (summary, store, console) does one job. New outputs are new listeners.
CommandControlRequestReplaces the "CH1|Cooling Fan" string. The request carries the device and the chamber state and has execute(), so the producer decides what and the consumer decides when.
Producer–ConsumerControlServiceReplaces the hand-written wait/notifyAll buffer that swallowed interrupts, with the JDK's ArrayBlockingQueue (capacity 5, as before).
RegistryCropRegistry, DeviceRegistryCrop and device names were hard-coded in control flow. A lookup by name is all that is needed; no factory hierarchy.
Composition root (DI)SVFRMS.createSimulationReplaces global static state. One place builds the object graph, so tests and the baseline harness can swap the sensor source.

Not used on purpose: a Strategy class per crop (crops differ only in numbers, so data is simpler); Singleton (it would recreate the global state we removed); Factory (nothing needs a family of products).

Build and run: mvn package (runs the tests and builds target/run.jar), then java -jar run.jar (or java -jar run.jar demo for the new crops). The baseline scripts and evidence are in baseline/; the full analysis is in docs/phase1-analysis.md and docs/phase2-design.md.
