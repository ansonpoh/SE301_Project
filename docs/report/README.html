1. Legacy System Analysis

SVFRMS runs an indoor vertical farm. Each growing chamber holds one crop. The system reads the chamber's sensors (temperature, humidity, soil moisture, light and nutrients), compares the readings with what the crop needs, raises alerts when something is wrong, switches on devices such as fans and pumps to fix it, and writes a report at the end of the day.

The program we were given is one Java class, SVFRMS (393 lines). Its main parts are:

PartWhat it does in the legacy code
Crop rulesprocessSensor() holds every crop's limits as hard-coded if statements.
Chamber simulationFour ChamberThreads (Tomato, Strawberry, Lettuce, Chili) each produce 20 rounds of random readings.
Device controladdControlRequest() puts "CH1|Cooling Fan" strings on a shared list; one ControlThread takes them off and calls activateControl().
Alerts and logginghandleEvent(type, ...) uses a string type ("LOG", "CREATE_ALERT", "TRACK_ACTION"...) to decide what to do.
ReportsgenerateDailyReport() and archiveAlerts() run on two threads; saveArchiveReport() writes archive/daily_report.txt.
Shared dataEverything lives in public static fields: lists, maps, counters and lock objects.

2.2 Concurrency problems

#ProblemWhy it goes wrong
C1Shared counters, e.g. totalWaterUsage += 2+= is read, add, write. Two threads can read the same old value and one update is lost.
C2ArrayList written by many threads (alerts, sensorLogs)ArrayList is not thread-safe. When we ran the legacy code, a chamber thread crashed with ArrayIndexOutOfBoundsException inside sensorLogs.add() and that chamber stopped being monitored.
C3Check-then-act on HashMap in getChamberState()if(!containsKey) put(...): two threads can both see "missing" and create two different objects.
C4ChamberState fieldsThe chamber thread writes new readings while the control thread does temperature - 5 on the same fields, with no lock.
C5ChamberSummary counterssummary.alerts++ runs on several threads with no lock.
C6Nested locks alertLock then reportLockHolding two locks at once is the setup for a deadlock: if any code takes them in the other order, both threads wait forever.
C7Report and archive threads raceThe two threads start together, so "Active Alerts" in the report changes from run to run.
C8Hand-made wait()/notifyAll() queueInterrupts are swallowed, and if the control thread dies the chamber threads block forever on a full queue.

3. Proposed Design

The goal is to keep what the system does but make it easy to change. The key changes are:

  • Split by responsibility. The monolith became 12 small packages (52 classes). Each class has one job, so a change touches one place.
  • Crops are data, not code. Crop limits live in crops.csv and chamber assignments in chambers.csv. A CropProfile must have a range for every sensor.
  • One rule instead of 25 copies. A single ThresholdRule reads the limit from the crop profile, so it never names a crop. A SensorFailureRule catches impossible readings.
  • Devices are objects. Each Device knows its effect (e.g. Cooling Fan: temperature −5, not below 18 C) and its resource cost. No more if(control.equals(...)).
  • Events instead of a string switch. Alerts and device activations are published on an EventBus. Storing, counting and printing are separate listeners.
  • No global state. Each FarmSystem owns its own stores, so tests can create one, run it and check it.
  • Thread-safe by design. Shared data is either immutable or guarded inside its own class. Threads are run by an ExecutorService.

Behaviour aligned with the specification. We kept every legacy feature but fixed the places where the legacy code did not follow the spec: every crop now uses all five ranges; alerts have INFO / WARNING / CRITICAL severity (based on how far the value is outside the range); low temperature starts the Heating Unit, high light starts the Shade Controller, high humidity starts the Dehumidifier and Ventilation System; impossible readings raise a Sensor Failure alert; and all five reports are produced. Water, energy and nutrient use is now counted when a device actually runs.

3.1 How SOLID is applied

PrincipleWhere it shows in the new code
SRPAlertStore only stores alerts, ConsoleEventPrinter only prints, ArchiveReportWriter only writes the file, ResourceMeter only counts usage.
OCPNew crop = new CSV row. New device, rule or report = new class registered in one list (StandardDevices, StandardRules, ReportGenerator). Existing classes are not edited.
LSPEvery SensorRule, Device and Report follows its interface fully, so any of them can be swapped in. Threads now use Callable/Runnable instead of extending Thread.
ISPSmall interfaces: SensorSource and SensorRule have one method; CropRepository is read-only. Event listeners are plain Consumers, so each listener only handles the event it needs.
DIPChamberMonitor depends on SensorSource, RuleEngine and Device abstractions. Only Main picks the concrete classes and passes them in.

4. Final Architecture

How a run works. Main loads the crops and chambers and builds a FarmSystem. FarmSystem starts one ControlWorker and one ChamberMonitor per chamber on a thread pool. Monitors read sensors, check rules, publish alerts and queue device requests (Figure 2). When every monitor has finished, FarmSystem closes the queue, waits for the worker to finish the remaining requests, then archives the alerts. Finally a read-only FarmSnapshot is taken and passed to the five reports and the archive writer. These steps run one after another, so the report is always consistent.

5. Concurrency Fixes

#FixWhere
C1Counters are AtomicLongs kept in a ConcurrentHashMap. addAndGet is one atomic step, so no update is lost.ResourceMeter, ReadingStatistics
C2No shared ArrayList is written without a lock. Alerts go into AlertStore, whose methods are synchronized. The unused per-reading log list was replaced by two atomic counters.AlertStore, ReadingStatistics
C3Each Chamber owns its ChamberState, so the lookup map is gone. Where a map is still needed, computeIfAbsent / compute create and update entries atomically.Chamber, ResourceMeter
C4ChamberState keeps its values private and every method is synchronized. adjust() does read-change-write as one step.ChamberState
C5The summary is an immutable ChamberActivity record, replaced with ConcurrentHashMap.compute(), which is atomic per chamber.ChamberActivityTracker
C6No thread ever holds two locks. Each class guards only its own data with one lock, and archiving is a single synchronized method. This removes the "hold and wait" condition needed for a deadlock.AlertStore
C7Archive and report now run in a fixed order after all threads finish (invokeAll + Future.get()), and reports read an immutable snapshot.FarmSystem, FarmSnapshot
C8ArrayBlockingQueue handles waiting and waking. Shutdown is an "end" marker placed after pending requests, so none are lost. Interrupts are restored, not swallowed. The worker catches errors per request so it never dies and leaves producers stuck.ControlQueue, ControlWorker

Threads are created by an ExecutorService; monitors are Callables, so any error inside a thread is returned through its Future instead of being lost. RandomSensorSource uses ThreadLocalRandom so threads do not compete for one shared Random.

Proof by tests. ConcurrencyTest runs 8 threads × 5,000 operations against ResourceMeter, AlertStore (adding while archiving), ChamberState and ChamberActivityTracker, and checks that the totals are exact. FarmSystemTest runs 4 chambers with a queue of size 1 (so producers must block) under a 10-second timeout to show there is no deadlock, and checks that every alert caused exactly one device activation.

Maintainability also comes from: small classes with clear names; immutable records for data passed between threads; validation in constructors (a crop missing a range, or an unknown crop in chambers.csv, fails at start-up with a clear message); and 30 JUnit tests covering boundary values, CSV loading and thread safety.

7. Design Patterns

PatternWhereProblem it solves / why we chose it
StrategySensorRule, Device, SeverityPolicy, ReportReplaces long if/else chains on crop and device names. Each behaviour is its own object behind one interface, so new behaviour is added without editing old code (OCP).
ObserverEventBus + listenersReplaces handleEvent("CREATE_ALERT"...). The monitor just publishes an alert; storing, counting and printing are separate listeners that can be added or removed freely.
CommandControlRequestA device request becomes a typed object (chamber + device) that can be queued and run later by another thread, instead of a "CH1|Cooling Fan" string that had to be split.
Producer–ConsumerControlQueue, ControlWorkerMonitors (producers) and the device worker (consumer) run at their own speed. A bounded queue limits pending work, and the Java library handles the waiting safely.
FacadeFarmSystemHides the wiring of buses, stores, queue and thread pool behind three calls: runMonitoring(), archiveAlerts(), snapshot().
RepositoryCropRepositoryThe rest of the system asks for crops without knowing they come from a CSV file. Storage could change (e.g. to a database) without touching the rules.
Dependency InjectionMainOne place creates concrete classes and passes them in through constructors. This is what lets tests use a fixed SensorSource instead of random values.

Patterns we chose not to use. Singleton: the legacy code's global static state is exactly the "singleton abuse" problem, so we removed it instead of adding more. State: devices are simply activated, with no on/off lifecycle, so a State pattern would add classes without solving a real problem (KISS).

How to run

java -jar run.jar (Java 25). The console shows alerts with severity and device actions, then the five reports; the full report is saved to archive/daily_report.txt. To build and test from source: mvn package.
